# allpaka

[![ci](https://github.com/themoretheless/allpaka/actions/workflows/ci.yml/badge.svg)](https://github.com/themoretheless/allpaka/actions/workflows/ci.yml)

Планировщик размещения языковой модели по нескольким машинам. Отвечает на
вопрос «стоит ли вообще разделять эту модель между этими машинами» - числами,
а не надеждой.

## Что здесь решается

Разделение модели по слоям (pipeline parallelism) - это гонка двух эффектов, и
исход решает сеть.

**В плюс:** каждая машина читает только свои слои и своей памятью, поэтому
`Σ(байты_i / bw_i)` меньше, чем `все_байты / bw_одной_машины`. Добавление
машины с быстрой памятью реально ускоряет декодирование.

**В минус:** на каждый проход платится сетевое время на каждом стыке.

```
t_прохода = Σ t_вычислений(узел) + Σ t_хопа(стык)
```

Хоп считается **односторонним**, а не round-trip: стадия отправляет активации и
идёт считать дальше, ack ей не нужен. Пайплайн из двух машин платит два
односторонних хопа за проход - вперёд скрытое состояние, назад выбранный токен -
то есть **один** round-trip суммарно, а не два. Начисление полного RTT на каждый
хоп удваивает мнимую цену сети и напрасно хоронит вполне пригодные линки.

Для одного интерактивного запроса слагаемые складываются, а не перекрываются.
Перекрытие стадий появляется только при нескольких одновременных запросах: это
поднимает суммарный throughput, но не снижает задержку отдельного токена.

Всё сводится к одному сравнению:

```
разрез выигрывает  <=>  сеть_на_проход  <  сэкономленные_вычисления_на_проход
```

Через стык идёт скрытое состояние `hidden_size x 2` байта, около 10 КБ, поэтому
пропускная способность почти не важна - важен **хвост задержки**, он платится на
каждом проходе.

Реальные числа для Qwen3-32B q8 (34 GiB) на паре M4 Max + RTX 5090. Экономия
вычислений от разреза - 56 мс на проход, это и есть бюджет на сеть:

| Линк | Сеть на проход | Итог |
|---|---|---|
| 10 GbE, p99 0.4 мс | 0.8 мс | 24.8 ток/с, **в 2.4 раза быстрее** одного мака |
| Wi-Fi, p99 30 мс | 30 мс | 14.4 ток/с, всё ещё быстрее, но скромно |
| Забитый Wi-Fi, p99 120 мс | 120 мс | разрез **проигрывает**, бюджет превышен |

Поэтому планировщик требует измерений и хранит их **по парам машин**: усреднить
10 GbE и Wi-Fi в одно число значит выбрать разрез, неверный на обоих стыках.

### Спекулятивное декодирование

Сеть платится за **проход**, а не за токен. Маленькая черновая модель на головной
машине предлагает `K` токенов, полная модель проверяет все `K+1` позиций за
**один** проход - для memory-bound модели батч из 6 стоит почти столько же,
сколько батч из 1. Один round-trip приносит несколько токенов вместо одного.

Чего спекуляция **не** делает: она не спасает разрез, проигравший по линку. Цикл
делит на одинаковый множитель принятых токенов и вычисления, и сеть, поэтому
сравнение выше не меняется. Это множитель пропускной способности для обеих
конфигураций, а не лекарство от задержки.

Что не работает вовсе: сжатие активации (10 КБ это микросекунды против
миллисекунд задержки), уменьшение числа разрезов (для двух машин он уже один),
tensor parallel вместо pipeline (all-reduce внутри каждого слоя - гораздо хуже).

## Команды

```bash
cargo build --release
```

Посмотреть архитектуру модели прямо из GGUF (число слоёв, ширина, KV-кэш):

```bash
allpaka inspect models/qwen3-32b-q8_0.gguf
```

Измерить реальную сеть - **каждую пару отдельно**. На одной машине:

```bash
allpaka bench --serve
```

На второй:

```bash
allpaka bench --connect 192.168.1.50:9797
```

Выводит throughput, p50/p99 round-trip и готовый TOML-фрагмент. Вписать его в
конфиг - паспортные цифры Wi-Fi для этого непригодны.

### Локальный inference (`serve`)

Свой движок (Rust + Metal, GGUF) с OpenAI-совместимым API:

```bash
allpaka serve --model models/qwen3-0.6b-Q8_0.gguf --bind 127.0.0.1:8099
```

Клиентские сабкоманды против запущенного сервера:

```bash
allpaka status                     # /health + /stats: какая модель, сколько контекста занято
allpaka chat "привет"              # один запрос к /v1/chat/completions
allpaka chat "что в заметках про Metal?" --rag   # с инструментами rag_search/rag_read
allpaka rag-test                   # smoke-тест RAG tool-loop; exit != 0 при регрессе
```

Роуты сервера: `POST /v1/chat/completions`, `GET /health`, `GET /stats`,
`GET /` (веб-чат). RAG-бэкенды и переменные — в разделе ниже.

### Проверка на двух машинах: пошагово

Инструмент кроссплатформенный (чистый std, собирается под
`x86_64-pc-windows-msvc`). На каждой машине нужен Rust
(<https://rustup.rs>, на Windows он поставит и MSVC Build Tools).

На Windows-PC (PowerShell):

Репозиторий на GitHub: `git clone https://github.com/themoretheless/allpaka`
(для Windows-сборки нужны только `crates/`, `Cargo.toml`, `Cargo.lock`).

```powershell
cd allpaka
cargo build --release
.\target\release\allpaka.exe bench --mem      # реальная скорость DDR4
.\target\release\allpaka.exe bench --serve    # затем ждать клиента
```

Первый запуск `--serve` спросит разрешение в Windows Firewall - разрешить для
частной сети, иначе клиент не подключится. Порт по умолчанию 9797.

На маке:

```bash
cargo build --release
./target/release/allpaka bench --mem
./target/release/allpaka bench --connect <ip-пк>:9797
```

IP посмотреть на PC через `ipconfig`. Три результата записать в `allpaka.toml`:

* `bench --mem` на PC -> `mem_bandwidth_gbps` узла `pc-ram` (это самое
  недостоверное паспортное число: одноканальная DDR4 вдвое хуже двухканальной);
* `bench --mem` на маке измеряет CPU-часть unified memory - для узла `mac`
  оставить паспортные 546, Metal читает быстрее CPU-кластера;
* `bench --connect` -> блок `[[links]] between = ["mac", "pc-gpu"]` (фрагмент
  печатается готовым). Если есть и Wi-Fi, и 10 GbE - измерить оба пути и
  записать лучший, планировщик по нему и решит, окупается ли разрез.

После этого `allpaka plan`/`allpaka fleet` считают уже по измеренным числам.
Протокол клиент-сервер покрыт loopback-тестом, так что сбой между реальными
машинами - это сеть или firewall, а не инструмент.

Создать конфиг кластера:

```bash
allpaka init > allpaka.toml
```

Дальше поддерживаются **два режима размещения**, и это разные ответы на разные
вопросы.

### По слоям: одна модель на все машины

```bash
allpaka plan --model models/qwen3-235b-a22b-Q2_K.gguf --ctx 32768
```

Режет модель по слоям и раскладывает по пулам памяти. Даёт самую крупную
возможную модель и самый быстрый ответ на **один** запрос, но машины связаны:
на каждый проход платится сетевой хоп, и эндпоинт получается один.

Порядок машин в конфиге не важен: планировщик перебирает все порядки, потому что
при неравных линках выбор головной машины меняет ответ.

Оценить спекулятивное декодирование - `--accept` нужно измерить, а не угадать:

```bash
allpaka plan --model models/big.gguf --draft models/qwen3-0.6b.gguf --draft-len 5 --accept 0.75
```

### По агентам: своя модель на каждый пул

```bash
allpaka fleet --model models/reasoner.gguf --model models/tools.gguf --model models/background.gguf --ctx 32768
```

Раскладывает **разные** модели по пулам, по одной на пул. Каждый агент получает
свой эндпоинт, машины между собой не общаются вообще. Модель у каждого меньше,
зато запросы идут параллельно и суммарная пропускная способность складывается
без потерь.

Размещение выбирается лексикографически: сначала максимум размещённых моделей,
потом максимум суммарной скорости. Непоместившиеся модели называются явно, а не
выбрасываются молча.

### Что выбрать

| | по слоям | по агентам |
|---|---|---|
| Модель | самая крупная | у каждого своя, меньше |
| Латентность одного запроса | лучшая | хуже |
| Параллельных запросов | 1 | по числу пулов |
| Связь между машинами | хоп на каждый проход | ноль |
| Отказ машины | падает всё | падает один агент |

Один пользователь, ждущий один ответ - по слоям. Агентный цикл с параллельными
вызовами - по агентам.

## RAG tool-calling для `/v1/chat/completions`

В `serve` добавлен `tools`-флоу:

* `rag_search(query: string)` — поиск по локальным `.md` заметкам.
* `rag_read(name: string)` — чтение одной заметки целиком.

Вызовы выполняются внутри сервера и добавляются в историю как `tool`-сообщения.

### Бэкенды поиска

Два бэкенда, выбор через `ALLPAKA_RAG_BACKEND` (`auto` по умолчанию):

* `mcp` — внешний `rag-mcp` сервер (DuckDB, BM25-индекс по чанкам, wiki-слой).
  `serve` спавнит его дочерним процессом и ходит по stdio JSON-RPC. Схемы
  инструментов для клиента не меняются.
* `grep` — простой поиск подстрок по директории заметок (как раньше).
* `auto` — rag-mcp, если бинарник и база на месте, иначе grep. Если MCP-ребёнок
  падает в рантайме, бэкенд молча деградирует до grep до конца процесса.

Настройка MCP-бэкенда:

* `RAG_MCP_BIN` — путь к бинарнику rag-mcp.
* `RAG_DB_PATH` — DuckDB база rag-mcp.
* `RAG_MCP_SEARCH_MODE` — режим поиска rag-mcp (по умолчанию `lex`).

Переменные окружения:

* `ALLPAKA_RAG_TOOLS` — `0` выключает RAG-инструменты (по умолчанию включено).
* `ALLPAKA_RAG_BACKEND` — `auto|mcp|grep` (по умолчанию `auto`).
* `ALLPAKA_RAG_NOTES_DIR` — директория с заметками (fallback к `RAG_INGEST_ROOTS`; для MCP-бэкенда пробрасывается как `RAG_INGEST_ROOTS` ребёнку).
* `ALLPAKA_RAG_SEARCH_MAX_RESULTS` — максимум совпадений поиска (по умолчанию `5`).
* `ALLPAKA_RAG_SEARCH_MAX_LINES` — максимум строк из одной заметки (по умолчанию `6`).
* `ALLPAKA_RAG_AUTO_TOOLS` — `1|true|yes|on` инжектирует схемы `rag_search`/`rag_read` автоматически, если `tools` не переданы.
* `ALLPAKA_RAG_MAX_TOOL_ROUNDS` — сколько итераций tool-loop делать (по умолчанию `2`).
* `ALLPAKA_RAG_READ_MAX_CHARS` — лимит символов ответа `rag_read` (по умолчанию `12000`).

Клиентские сабкоманды бинарника: `allpaka status`, `allpaka chat "<промпт>" [--rag]`,
`allpaka rag-test` (smoke-тест tool-loop, exit != 0 при регрессе).
Интеграционные тесты: `cargo test -p allpaka-cli --test plugin_smoke -- --test-threads=1`.

Пример `tools`:

```json
[
  {
    "type": "function",
    "function": {
      "name": "rag_search",
      "description": "Search notes",
      "parameters": {
        "type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"]
      }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "rag_read",
      "description": "Read one note",
      "parameters": {
        "type": "object",
        "properties": {"name": {"type": "string"}},
        "required": ["name"]
      }
    }
  }
]
```

## Структура

- `crates/allpaka-core` - типы и модель стоимости. Никакого I/O, только
  арифметика, поэтому она покрыта тестами.
  - `plan.rs` - перебор разрезов и всех порядков машин, проверка вместимости,
    вердикт.
  - `fleet.rs` - размещение по агентам: разные модели по пулам, по одной на пул.
  - `replicate.rs` - одна и та же модель на каждом пуле, нулевая связанность.
  - `fabric.rs` - сеть по парам: 10 GbE между одними, Wi-Fi между другими.
  - `node.rs` - машина: доступная память и её пропускная способность.
  - `model.rs` - форма модели: слои, ширина, объём на стык.
  - `link.rs` - одно измерение линка, односторонняя и round-trip цена.
  - `speculation.rs` - спекулятивное декодирование: сколько токенов даёт проход.
- `crates/allpaka-cli` - бинарь `allpaka`.
  - `bench.rs` - измеритель сети и движка.
  - `serve.rs` - OpenAI-совместимый сервер: chat API, сессия с KV-кэшем,
    RAG tool-loop (см. раздел про RAG).
  - `client.rs` - клиентские сабкоманды `status` / `chat` / `rag-test`
    (HTTP по голому TcpStream + serde_json, без зависимостей).
  - `rag_mcp.rs` - stdio JSON-RPC клиент к внешнему `rag-mcp` (BM25/DuckDB):
    spawn, MCP-handshake, таймауты, откат на grep.
  - `verify.rs` - сверка логитов с llama-server.
- `crates/allpaka-cli/tests/plugin_smoke.rs` - интеграционные тесты: serve
  end-to-end, RAG через mcp/grep/fallback, rag-mcp по stdio. Тесты
  сериализованы общим мьютексом (один порт, одна GPU); скипаются, если нет
  модели или бинарника rag-mcp.
- `plugins/allpaka`, `plugins/rag-mcp` - Kimi-плагины (личный маркет):
  движок и RAG как MCP/скилл. Установка: вкладка «个人» → ＋.

## Тесты и CI

```bash
cargo test --workspace    # юниты + GPU-тесты + smoke (локально, с Metal)
```

GPU-тесты и smoke-тесты скипаются там, где нет Metal-устройства или моделей
(GitHub-раннеры), поэтому CI зелёный и на них. Workflow:
`.github/workflows/ci.yml` (macos-14, `cargo test --workspace` на push).
Полное покрытие (реальные кернелы + end-to-end RAG) даёт локальный прогон.

Оптимизации MoE-prefill под Metal (GPU-роутинг, fused SwiGLU, замеры против
llama.cpp, список фальсифицированных идей) задокументированы в
[docs/moe-prefill.md](docs/moe-prefill.md).

## Откуда берутся числа

- **Веса** - размер файла GGUF на диске. Это честный footprint на выбранной
  квантизации, в отличие от оценки по числу параметров.
- **Слои, ширина, KV-головы** - из заголовка GGUF, а не из таблицы.
- **Пропускная способность памяти** - из пресета (`allpaka presets`),
  умноженная на `bandwidth_efficiency` (по умолчанию 0.7, столько реально
  выдают ядра llama.cpp). Пресеты - это паспортные цифры вендора,
  переопределяйте их измерениями.
- **Сеть** - только измерение, пресетов нет намеренно. Неизмеренный стык
  блокирует разрез через него, а не подставляет оптимистичную догадку. Общий
  fallback задаётся секцией `[link]`, если он вам нужен.

## Что дальше

Свой движок уже есть и работает (`serve`: Metal-backend, MoE, GPU routing,
RAG tool-loop). Ближайшие шаги:

- Распределённый инференс по измеренным линкам: планировщик выдаёт раскладку
  слоёв, движок поднимается на узлах, активации идут по сети. Модель стоимости
  в `plan.rs` про физику, а не про реализацию - она остаётся той же.
- Self-hosted CI раннер на машине с Metal: тогда CI покроет GPU-кернелы и
  smoke-тесты с настоящими моделями, а не только CPU-часть.
