# Gemma 3 12B against llama.cpp (RTX 5090)

Model: `bartowski/google_gemma-3-12b-it-GGUF`, `Q4_K_M` (6.79 GiB).
llama.cpp: `third_party/llama.cpp/build-cuda` (`97e4ca7`), same session, GPU
otherwise idle.

## What runs

The `gemma3` architecture (`Experimental`), following llama.cpp's
`src/models/gemma3.cpp`:

- token embeddings scaled by sqrt(hidden);
- sandwich norms (`post_attention_norm` on the attention output, `post_ffw_norm`
  on the FFN output, both before the residual add); the GGUF norm weights
  already carry Gemma's +1;
- GeGLU with tanh GELU;
- sliding-window local layers: `layer % 6 < 5` attend over the last 1024
  positions (`LLAMA_SWA_TYPE_STANDARD`), rotated with base 10000; global
  layers use base 1e6 with linear scaling 8 (frequencies / 8).

Paths, all on the GPU while the context fits the 1024 window:

- decode: the fused whole-token path (`geglu_tanh` and `rmsnorm_add_f32`
  kernels, post-norms in the decode norm arena, a second RoPE table for the
  local layers); `gpu path decode: attempts=32 successes=32 declines=0`;
- prefill: the GPU-resident fused prefill (post-norms and GeGLU on the
  device, per-layer RoPE table, MMQ GEMMs on quantized weights).

Past the 1024 window: the fused prefill's flash-attention mask carries the
window (`allpaka_fa_set_window`, part of the slot key), the per-layer decode's
GPU attention shifts its K/V start to the window, and kernels without a window
(`attend_gqa_batch`, the non-fused prefill block) decline to the per-layer
path, whose CPU attention pulls device-written K/V back first.

## Bugs found on the way

Long prompts exposed five defects, four of them outside Gemma code:

1. `matvec_batch` (CUDA): a batch of GEMMs sharing one input grew the output
   arena inside the loop, and `ensure_arenas` reallocates zeroed, so the
   earlier items' outputs were lost. Gemma's 15360-wide gate/up at 100+ rows
   was the first shape to hit it (gate came back as zeros). The arenas are now
   sized for the whole batch first.
2. Fused prefill uploaded the RoPE table only when its length changed; Gemma's
   local and global tables have the same length, so every layer rotated with
   layer 0's table. The upload is now keyed on the source too.
3. GPU paths write K/V on the device alone; a CPU attention that follows (the
   window past 1024, or any CPU fallback) read the stale host copy.
   `KvCache::pull_gpu_range` brings the rows back first on a discrete GPU.
4. The bridge's f16-weight GEMM converts activations to f16, which Gemma's
   outlier activations do not survive; Gemma's prefill GEMMs keep quantized
   weights (`allpaka_ggml_set_quant_gemm`, llama.cpp's MMQ), at no measured
   speed cost.
5. A second RoPE table mid-chunk reused the pinned staging of the first
   upload while that copy could still be queued (1106-token prefill: 0.79,
   after the fix 0.29); only the first upload of a chunk is pinned now.

Unchanged by these fixes, checked in the same session: Llama-3.1-8B passes
three prompts at `--tol 0.3` with identical numbers; Qwen2.5-7B passes two and
fails the third at decode step 23 (0.7077), exactly as the commit before
Gemma support does; `cuda_decode_multi_parity` on Qwen2.5-7B agrees 64/64 in
all four sessions.

## Run-to-run spread on the 3011-token prompt

The fused prefill is not bit-deterministic run to run: the same binary gives
prefill 0.1967 or 0.2258 and, along the greedy path that follows, a decode
step 10 gap of 0.9063 against the 0.9 tolerance (argmax equal) in some runs and
a full 32-step pass at 0.83 in others. The build before the merge with
`origin/main` behaves identically, so this is not a merge regression; the
decode tail on this prompt sits at llama.cpp's own spread (its CUDA and CPU
builds differ by up to 0.86 on a Qwen2.5-7B prompt of this kind).
