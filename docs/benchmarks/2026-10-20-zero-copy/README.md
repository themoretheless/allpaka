# Metal: zero-copy residual → output head, 2026-10-20

На Apple M4 Max реализована передача промежуточного residual-вектора из fused-prefill в CPU-нормализацию и затем в Metal-проекцию без промежуточного копирования данных.

## Что изменилось

- `Activation` владеет обычным `Vec<f32>` либо завершённым shared Metal-буфером.
- Перед передачей буфера CPU завершаются все GPU-записи. Буфер отсоединяется от рабочей арены; следующий prefill получает другую allocation и не может перезаписать выданные данные.
- CPU выполняет output-нормализацию прямо в shared-памяти. `QuantMat::matmul_activation` передаёт тот же буфер и смещение Metal-шейдеру, используя прежние kernels и tiling.
- После использования allocation возвращается в ограниченный spare-slot. Невыровненные смещения и неподдерживаемые операции используют прежний staging/fallback.
- Выдать буфер можно только один раз за активный chunk и только с его фактической длиной: незаполненный хвост allocation недоступен.
- `ALLPAKA_PREFILL_ZERO_COPY=0` включает копирующий путь для A/B; по умолчанию Metal использует shared-путь. CUDA и CPU сохраняют прежнюю модель памяти.

Это не удаление всех memcpy в движке: начальная загрузка embeddings остаётся; финальные logits и публичные API, явно возвращающие CPU `Vec` скрытых состояний, продолжают материализовать эти результаты. Межслойные `pf_x`/`pf_hs` в fused-prefill и раньше оставались на GPU.

## Протокол

Модель: официальный `Qwen/Qwen3-0.6B-GGUF`, файл `Qwen3-0.6B-Q8_0.gguf`, [источник](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/resolve/main/Qwen3-0.6B-Q8_0.gguf).
SHA-256: `9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031`.

Основное сравнение выполняется одним зафиксированным release-бинарником с переключателем `0/1`: 7 пар процессов на каждый PP, порядок AB/BA чередуется. В каждом процессе один прогревочный и три измеряемых прохода. PP=512/2048, chunk=512; decode — 32 обычных `forward` из независимого однотокенного контекста. Токены одинаковые, проверяются конечные logits и сгенерированные токены; счётчики подтверждают shared-handoff и прямое чтение head-входа. Это сравнение Allpaka с самим собой, без llama.cpp.

Во время работы в checkout менялся и другой код. Поэтому сравниваются режимы одного неизменяемого бинарника, а не два подвижных состояния checkout. SHA бинарников, model SHA, git/base и сырые выборки сохранены рядом. Рабочая машина использовалась другими приложениями: измерения inference шумные, вывод о выигрыше делается отдельно от микробенча.

`before-512.json`/`.log` — диагностический прогон исходного CLI до изменения. CLI записал полный finite-отчёт, но затем завершился с кодом 1 из-за отсутствующего внешнего `airbug bench` runner. Он не используется как основное A/B-доказательство. Первый pilot, пересёкшийся с GPU-тестом корректности, исключён.

## Воспроизведение

```sh
cargo build --release -p allpaka-model --example shared_activation_bench
python3 scripts/bench-shared-activations.py \
  target/release/examples/shared_activation_bench /path/to/model.gguf /tmp/shared-ab-new

cargo run --release -p allpaka-backend --example shared_handoff_bench

cargo test -p allpaka-backend -p allpaka-model --lib --test gpu_shared_activations
ALLPAKA_TEST_MODEL=/path/to/model.gguf cargo test --release -p allpaka-model \
  --test prefill_shared_parity -- --ignored
```

Запускать последовательно, без параллельного GPU-тестирования. Микробенч измеряет только завершение/handoff + CPU-нормализацию последней строки + drop, без начальной загрузки и без вычислений модели: 9 чередующихся пар, по 100 измерений после 10 прогревочных итераций на режим и размер. Его результаты нельзя переносить на throughput всей модели.

## Финальные результаты

### Вся модель, токенов/с (больше лучше)

Столбцы скоростей — медианы медиан процессов. Парное изменение — медиана отношений внутри пар; из-за дрейфа нагрузки оно может отличаться от отношения двух общих медиан.

| PP | Фаза | Copy | Shared | Парное изменение | Bootstrap 95% |
|---|---|---:|---:|---:|---:|
| 512 | prefill | 7991.9 | 7932.6 | -1.27% | -13.87…+9.89% |
| 512 | decode | 295.6 | 254.4 | -8.86% | -57.41…+43.50% |
| 2048 | prefill | 5210.5 | 5328.1 | +5.73% | -16.49…+13.68% |
| 2048 | decode | 185.9 | 200.3 | +10.54% | -11.70…+36.18% |

**Ускорение end-to-end не подтверждено.** Все интервалы включают ноль; даже неизменённый decode сильно колеблется. Это не доказательство отсутствия регрессии при изолированной нагрузке. Подтверждены удаление копирования и уменьшение стоимости самой передачи буфера. Один прогон на M4 Max не квалифицирует M1/M2/M3.

Во всех 28 финальных процессах конечные logits совпали точно (`max_logit_diff_vs_reference = 0`); последовательности decode совпали в каждой паре. На один 512-токенный chunk устраняются 2 МиБ materialization residual и 4 КиБ повторного staging head-входа (счётчики включают прогрев).

Основные данные находятся в `validated/`, микробенч — в `handoff-validated*`. `exploratory-1/`, `exploratory-2/` и исходный `handoff.jsonl` оставлены как предварительные серии; они не смешиваются с финальной статистикой.

## Проверки

- 40 backend unit tests, 43 model unit tests, 1 Metal ownership/alignment regression: все прошли.
- Дополнительный реальный model parity test прошёл; проверяет `forward_batch`, `forward_batch_hidden`, `forward_batch_full`, `forward_batch_full_hn` на 16, 33 и 512 токенах.
- Регрессия владения проверяет, что новый chunk не меняет уже выданный буфер; CPU-нормализация сохраняет его адрес; повторная выдача, неверная длина и переполнения отвергаются; невыровненный вход использует staging.
- Полная проверка CUDA/Linux и других Apple SoC не выполнялась.
