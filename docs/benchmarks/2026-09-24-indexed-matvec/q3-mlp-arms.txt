# q3_k load schedule: matvec_q3_k_mlp against the incumbent

The last mechanism on the `q3_k` list, and the only one that could have shipped
for free. `q3-locality-arms.txt` killed the interleaved-plane repack by measuring
run locality, which left one branch of the original diagnosis untested: "if
removing the arithmetic does not move it, it is latency and only more bytes in
flight per lane helps" (`README.md`, the paragraph under the shape table). The
incumbent `matvec_q3_k_mv` issues each block-row's 16 ushort weight reads
interleaved with the FMA chains that consume them, so a lane may have only a few
of them outstanding at a time. `matvec_q3_k_mlp` is that kernel with the sixteen
loads hoisted into locals ahead of both inner loops - same bytes, same addresses,
same widths, same arithmetic, same reduction, same geometry. One property
changes: how many weight loads a lane can have in flight. No memory cost, no
repack, no format change - if it won, it was shippable as-is.

Shape `[4096,1536]` x8 indexed (the 235B's own dispatch), 12 rotating expert
sets, feed=32, `q5_shape_ratio_against_q4`, one process per arm, `q4_k` as the
in-run meter. 6 reps x 4 arms, arm order rotated by one slot per rep so position
cannot be the experiment. Load over the sequence: the same harness's `q4_k` meter
went 310 -> 747 ps/row/block between rep 1 and rep 6 as the desktop filled up,
which is exactly the drift the ratio is built to absorb - rep 6's `mlp` run had
an absolute 1269 ps and a ratio of 1.779, indistinguishable from rep 1's 593 ps /
1.739.

```
arms=("" mlp nomath nomath_norowstep)   # "" = incumbent
for rep in 1 2 3 4 5 6; do
  for i in 0 1 2 3; do
    arm=${arms[$(( (i + rep) % 4 + 1 ))]}   # rotated one slot per rep
    env ALLPAKA_Q3_PROBE=$arm ALLPAKA_Q5AB_N_OUT=4096 ALLPAKA_Q5AB_N_IN=1536 \
        ALLPAKA_Q5AB_SETS=12 ALLPAKA_Q5AB_PER_WAIT=32 \
      cargo test -p allpaka-backend --test gpu_ffnbench -- \
      --ignored --nocapture --test-threads=1 q5_shape_ratio
  done
done
```

## Result (ratio to the in-run `q4_k` meter; all 24 runs kept)

| arm | kernel | n | mean | sd | range | vs incumbent |
| --- | --- | --- | --- | --- | --- | --- |
| incumbent | `matvec_q3_k_mv` | 12 | 1.767 | 0.055 | 1.683-1.882 | - |
| mlp | `matvec_q3_k_mlp` | 6 | 1.763 | 0.045 | 1.684-1.808 | **-0.26%** |
| nomath | `matvec_q3_k_nm` | 6 | 1.358 | 0.019 | 1.332-1.384 | -23.1% |

Per-rep, paired where both arms ran in the rep: -2.9%, +0.6%, +5.6%, +4.4%,
-10.5%, -0.3% - four signs in six, mean -0.5%, spread far wider than the effect.
The `nomath` column is the instrument check: in the same processes, at the same
loads, the harness resolves a real `q3_k` difference to 23.1% with sd 0.019. So
this is a null from a working meter, not an insensitive one.

## What this closes

Bytes in flight per lane is not `q3_k`'s cost. Either the scheduler was already
issuing those loads ahead of their consumers, or outstanding-load count is not
what the block-row is waiting on - and the two readings decide the same thing,
because there is no schedule left inside this kernel to win. The mechanism list
is now closed at five entries, all measured on the model's own dispatch:

| mechanism | arm | effect on `q3_k` / `q4_k` | shippable? |
| --- | --- | --- | --- |
| dequant arithmetic | `nm` | -22.9% | capped at that: the port's whole prize |
| weight load width (110 -> 112 B, ushort -> uint) | `nw` | -4.6% | costs ~26 GiB of private copy |
| weight load count (row 1 reuses row 0's bytes) | `ns` | -33.2% | no - real rows own different weights |
| run locality (one contiguous 32-byte window) | `ic` / `_icw` | +2.0% / +4.0% | no - wrong sign |
| load schedule (16 loads hoisted ahead of consumers) | `mlp` | **-0.26%** | no effect to ship |

What is left of `q3_k`'s 1.77 is therefore not inside `matvec_q3_k_mv`: it is
0.44 of arithmetic plus ~1.3 of per-block cost that no reordering, widening,
locality or pipelining of the same loads reaches. The only arm that moved it
materially was the one that reads fewer weight bytes, which the format's row
ownership forbids.

`matvec_q3_k_mlp` computes a real dot product, unlike its four siblings, and it
was never promoted - so it was never gated on numerical correctness, and the CPU
parity check is not part of this artifact. That is deliberate: a -0.26% candidate
does not need to be proven right, only recorded as not worth shipping. If it is
ever revived, the gate is `gpu_parity::indexed_matvec_matches_cpu_reference`
against the incumbent's output, not this table.
