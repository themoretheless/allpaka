# Llama 3.1 8B on the CUDA path against llama.cpp (RTX 5090)

Model: `bartowski/Meta-Llama-3.1-8B-Instruct-GGUF`, `Q4_K_M` (4.58 GiB).
llama.cpp: `third_party/llama.cpp/build-cuda` (`97e4ca7`), same session, GPU
otherwise idle (other sessions share the card; checked before each run).

## Path

`allpaka bench --engine`: `gpu path decode: attempts=32 successes=32
declines=0`. The loader permutes Wq/Wk from NORM to NEOX order (roadmap P9),
and since this change also applies `rope_freqs.weight` (Llama 3.1 "llama3"
rope scaling): each RoPE pair's inverse frequency is divided by its factor, as
llama.cpp's `freq_factors` do. `ALLPAKA_NO_ROPE_FREQS=1` turns it off; at
these short positions the factors only touch the slow pairs, so both settings
agree on every greedy token.

## Parity: `allpaka verify --decode 32 --tol 0.3` against `llama-server -ngl 99`

| Prompt | Prefill max top-10 diff | Decode max diff (32 steps) | Argmax |
|---|---|---|---|
| `The capital of France is Paris. The capital of Japan is` | 0.2252 | 0.1523 | 32/32 |
| `Write a short poem about the sea.` | 0.0700 | 0.2419 | 32/32 |
| `def fibonacci(n):` | 0.1486 | 0.3024 | 32/32 |

All three pass at `--tol 0.3` (decode 0.48). With the default 0.15/0.24 they
fail on the tail: the largest differences sit on tokens near log-prob −7.
That spread is not Llama-specific:

- llama.cpp against itself (cached decode vs uncached batch scoring of the
  same contexts, poem prompt): up to 0.20.
- allpaka's CPU path on Llama: decode up to 0.57.
- Qwen2.5-7B (already in the matrix) on the GPU path, same prompts: decode up
  to 0.42.

## A trap met on the way

A llama-server left on port 8091 from an earlier Qwen run answered the Llama
verify, so every argmax "disagreed". Check `/props` `model_path` before
trusting a verify result.
