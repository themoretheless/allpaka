Q5_0 `_mv` on GLM-4.5-Air decode: 32 process pairs, alternating order, gated at load < 5
==============================================================================================

Question
--------
The Q5_0 llama-structure matvec port (matvec_q5_0_mv) measured 2-3x faster than the scalar
path on the down-shape microbench, and the byte-share arithmetic made a pre-registered
prediction of +6-7% on GLM-Air decode. The gate written before that run, in
../2026-09-24-indexed-matvec/q5_0-mv-port.txt, was ~30 pairs on a machine that stays under
load 5, because the 11-pair attempt it replaced had a +-20% per-pair noise floor. This is
that run.

Method
--------
Arms: ALLPAKA_Q5_0_MV=1 (the shipped default) vs =0 (the scalar path it replaced). Each run is
a fresh process:
  env ALLPAKA_Q5_0_MV=$arm ALLPAKA_BENCH_PP=480 ALLPAKA_BENCH_TG=64 \
      ALLPAKA_BENCH_SKIP_MTP=1 ALLPAKA_PROFILE=max-performance \
      ALLPAKA_BENCH_REPORT=$rep ./target/release/allpaka bench \
        --engine models/GLM-4.5-Air-Q4_K_M-00001-of-00002.gguf
32 pairs; odd pairs run AB (mv=0 first), even pairs BA, so a position or drift effect cancels
instead of masquerading as the knob - the failure mode documented in the five-arm loop of
../2026-09-24-glm-knobs/README.md. Two warmup pairs discarded. Before every run the driver
waits for the 1-minute load average to drop below 5 (sysctl vm.loadavg, 30 s poll, 40 tries);
the highest value seen at any arm start in a pair is reported in its row. No pair is missing an
arm, so nothing was excluded on that ground (0 of 32). Each pair is then labelled by the band
criterion used in the Analysis: clean = both arms at or above 35 decode tok/s, this model's
historical cool-machine band; disturbed = either arm below it.

Verdict
-------
Ship rule satisfied: the effect is real, and the shipped default `ALLPAKA_Q5_0_MV=1`
(crates/allpaka-backend/src/gpu/metal.rs:15775-15780) stands and needs no change. The port is
merged with a measured win and a knob-off regression path (=0 restores the scalar kernel that
this run measures against).

The number to quote is the clean band: **+16.05% decode, SEM 1.59, 15/15 pairs positive,
trimmed +15.95%**, at absolutes 39.67 -> 45.95 tok/s on GLM-4.5-Air Q4_K_M with pp480/tg64.
The whole-session +20.50% is the same sign but must not be quoted: it mixes 15 pairs whose
absolute level sits far below this model's historical decode band, and a ratio computed
against disturbed arms is noise with a mean.

Gate honesty. The gate written before the run was "~30 pairs on a machine that stays under
load 5". 30 usable pairs were obtained, and every run in the clean band was started under a
1-minute load average below 5 (highest 4.94). But the load gate alone did not buy clean
runs: 15 of the 30 usable pairs sat under load 5 and still printed below 35 tok/s, and their
per-pair spread (sd 31.53) is 5x the clean band's (sd 6.14). Load average is a coarser
instrument than the throughput band; the band, not the gate, is what makes a pair usable.

Calibration finding, and its resolution. The byte-share arithmetic predicted +6-7% and the
measurement is +16.05%, ~2.3x the pre-registered figure. Recomputing from the two artifacts
already in the repo shows the model was fine and the input ratio was not. The prediction in
../2026-09-24-indexed-matvec/q5_0-mv-port.txt is "0.71 GiB of 6.1 per token at 133 against
175 GB/s", i.e. a kernel-rate ratio of 1.32 taken from one interleaved indexed pair's raw
numbers; the same file's own summary of that geometry is ~1.9x normalized to the in-run Q8_0
meter, and 2.8x in the shape table's indexed arm. Feeding those ratios back through the
prediction's own arithmetic (0.28 decode-time share, gain = 1/(1-share+share/R)):

    R = 1.32  ->  +7.3%   (what was pre-registered)
    R = 1.9   ->  +15.3%  (the port log's normalized indexed ratio)
    R = 2.8   ->  +22.0%  (the port log's shape-table indexed arm)
    measured  ->  +16.05% +- 1.59 SEM, which inverts to R = 1.98

So the end-to-end measurement sits on the indexed-geometry micro measurement, half an SEM
from 1.9x and far from 1.3x. No new GPU run was needed to find this, and no byte-share
under-prediction has to be believed: the correction is to take the rate ratio at the
geometry the model actually dispatches - indexed for MoE experts - not at whichever
interleaved pair was handy. Two honest limits: the 28% time share was itself derived from
rates, so this is a consistency repair rather than an independent confirmation of the ratio;
and the arithmetic assumes the Q5_0 traffic does not overlap with the rest of the token,
which is exactly the assumption the earlier q5_k case ("the bytes, not the issue slots, set
the pace") survived and the q3_k series did not.

What this does NOT say. It does not close the GLM-vs-llama parity question in
docs/benchmarks/allpaka-vs-llama-metal-status.md: that 0.86x was measured at tg32 against a
llama arm, and this table is allpaka-vs-allpaka at tg64 with no llama arm in the sequence.
39.67/45.95 here are not comparable to the 38.8 tok/s tg32 triple recorded earlier, and no
parity claim should be built on this file until a same-command llama arm is run beside it.

Appendix: the disturbance is not drift and not load (recomputed from the raw sequence)
---------------------------------------------------------------------------------------
Usable pairs grouped in sixes, each group reduced to the median of its better arm, its worse
arm, and the median of the pair's highest 1-minute load reading:

    pairs 3-8     better arm 47.1  worse arm 41.0  median load 3.63
    pairs 9-14    better arm 25.0  worse arm 22.0  median load 3.83
    pairs 15-20   better arm 39.1  worse arm 30.8  median load 2.36
    pairs 21-26   better arm 45.1  worse arm 34.3  median load 3.82
    pairs 27-32   better arm 42.8  worse arm 36.0  median load 4.81

Two things follow, and both are about the instrument rather than the knob.

1. The session did not heat its way into the disturbed pairs. The worst window is pairs
   9-14, in the middle of the sequence, and the run recovered to 45 tok/s by 21-26. A
   thermal-drift story would be monotone; this one is not, so "the machine was busy" in the
   burst sense is the only reading that fits.
2. The load average does not predict the band. The cleanest window in the table
   (pairs 15-20 by worse-arm, and 21-26 and 27-32 by better-arm) carries a median load of
   2.36, 3.82 and 4.81, while the worst window carries 3.83. Reading down the two columns,
   a low load gate value is found next to disturbed pairs and a high one next to clean
   pairs. The gate is therefore not the instrument that made this measurement usable - the
   band criterion is, and the same-run prefill of 336-374 tok/s in the clean band (against
   90-264 in disturbed pairs) is the sharpest version of it: it needs no history of the
   other engine, only the engine's own known ceiling.

Consequence for the next measurement in this directory: gate on the prefill thermometer and
the decode band, and treat vm.loadavg as a weak precondition, not as the check.
