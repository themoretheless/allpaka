## Amendment 2026-09-25T23:31Z - the `policy bool via parse_bool` class could label a knob whose read never calls parse_bool

Found by re-reading the tools for instruments that cannot speak, the same sweep that
turned up the dead drift veto in `../2026-09-25-glm-shared-stagger/`. The census entry
was the bare word:

    ("policy bool via parse_bool", r"parse_bool"),

Every other idiom pattern interpolates the knob name into its regex; this one did not, so
it matched any 12-line window in which the word `parse_bool` happened to appear. In
`crates/allpaka-backend/src/profile.rs` one `parse_bool(&value)` call serves a six-name
loop, and the function definition `fn parse_bool(value: &str)` sits eight lines below the
last read in that loop - close enough to catch `ALLPAKA_ATTN_SPLIT` at
`profile.rs:81`, which is not a bool at either of its sites:

    policy.attention_split = std::env::var("ALLPAKA_ATTN_SPLIT")
        .ok()
        .and_then(|v| v.parse().ok());          # runtime.rs:38
    resolved = resolved.override_attention_split(value.parse().ok());   # profile.rs:81

So the row above (`runtime.rs:38 -> unclassified; profile.rs:81 -> policy bool via
parse_bool`, marked MIXED) was wrong in both halves, and its MIXED mark was an artefact:
the two sites agree, they read a numeric selector. The corrected row, after the pattern
fix, is

    | `ALLPAKA_ATTN_SPLIT` | runtime.rs:38 -> numeric parse (a selector, not a flag);
      profile.rs:81 -> numeric parse (a selector, not a flag) |            (not MIXED)

and the class census gains

    - numeric parse (a selector, not a flag): 1 (ALLPAKA_ATTN_SPLIT)

replacing

    - policy bool via parse_bool / unclassified: 1 (ALLPAKA_ATTN_SPLIT)

What changed in `census.py`: the `parse_bool` class now has two name-anchored patterns -
the tuple form `("ALLPAKA_X", "field")` that a `for (env, field) in [...]` loop reads
through `env::var(env)` + `parse_bool(&value)`, and a direct read whose next 240
characters call `parse_bool(&` - the `&` being what keeps a knob from matching the
*definition* below it rather than a call. A `numeric parse (a selector, not a flag)` class
was added, ordered after both existing numeric-sweep patterns so that a `.parse()` with an
explicit default keeps the class that names the default.

Re-ran after the fix and diffed against the table above: this is the only classification
that moves. The six genuine loop knobs (`ALLPAKA_NORMFLAG`, `ALLPAKA_DECODE_SERIAL`,
`ALLPAKA_PF_DEFER`, `ALLPAKA_PF_ONEBUF`, `ALLPAKA_GPU_ROUTE`, `ALLPAKA_MM_PIPE`) keep
their `policy bool via parse_bool` second site and their MIXED marks, which is the finding
this table exists to make - `ALLPAKA_GPU_ROUTE=2`, say, means ON in `runtime.rs:44` and
leaves the profile override untouched, so the two reads disagree about what a value means.
The one number in `docs/decode-opts.md` that could be affected is its
"instrument, not lever" row listing `ALLPAKA_ATTN_SPLIT` with default `off`: checked, and
it stays right, because unset parses to `None` and the policy keeps its default.

Not republished above: the table's line numbers are the 21:43Z capture at tree `dcdc131`,
and `crates/allpaka-backend/src/gpu/metal.rs` in this worktree has moved since (another
session is editing it), so a re-run today prints the same classifications at shifted
`metal.rs` line numbers. To reproduce this census at the published tree, check out
`dcdc131` and run the command in the header from there.
