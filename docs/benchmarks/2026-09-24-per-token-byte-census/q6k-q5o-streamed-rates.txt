# What this window says, beyond filling the two missing rates:
#
# 1. q6_k is a full-rate format. 471.7 GB/s at [4096,1536] against q4_k's
#    472.2 in the same run, and 459.7 vs 468.6 at [1536,4096]. Its cost per
#    token is 1.46x q4_k's in bytes and not at all in bytes/s, so a ledger
#    that treats q6_k as slow is wrong: q6_k carries 27.3% of the 30B's
#    decode weight bytes and 3.4% of the 235B's, and it runs at q4_k's rate.
# 2. q5_0 is NOT at q8_0's rate. 396.6 against 495.6 GB/s, i.e. 0.80x, where
#    the byte-share arithmetic that justified the _mv port assumed 400 and the
#    post-port summary implied parity with q8_0 by treating both as
#    "non-k-quant". The assumption survives (396.6 vs 400 is a 0.9% error in
#    the ledger), but it is now a measurement rather than an assumption.
# 3. Rates are shape-bound in one direction only. Swapping n_out and n_in
#    costs ~1% (q4_k 472.2 vs 468.6; q6_k 471.7 vs 459.7) and narrowing a
#    4096-wide row to 1408 costs 3% (q5_0 396.6 vs 383.6). What actually
#    moves is a dimension at 768: the 30B's q4_k gate/up at [768,2048] runs
#    386.7 (-18% vs the [4096,1536] arm) and its q6_k down at [2048,768] runs
#    363.9 (-23% vs the wide q6_k arms). Both 30B expert shapes sit at the
#    repo's narrowest recorded byte rates; the mechanism is not identified
#    here - 3 blocks per row at n_in 768 against 6-16 elsewhere is the
#    obvious candidate and untested. Consequence, and it cuts against the
#    earlier reading: the 30B ledger built from the wide table UNDER-states
#    its per-byte cost by ~20%, so its kernel sum goes from 3.96 to 4.92 ms
#    and the model explains 68% of its wall time instead of 54%. The
#    "30B is not byte-limited" verdict from section 2 was partly an artifact
#    of borrowing wide-shape rates (section 3 of time-ledger.txt).
# 4. Not measured, still open: none of these are dense lm-head rates. The
#    head (q6_k 561.1 MiB on GLM, 749.4 on 235B, 499.4 on the 30B, 6-9% of
#    each token) goes through the un-indexed matvec path, which this bench
#    does not exercise; using an indexed rate for it is an approximation and
#    the ledger says so.
