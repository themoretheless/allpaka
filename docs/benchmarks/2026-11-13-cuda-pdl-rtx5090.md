# CUDA programmatic dependent launch (PDL) on RTX 5090, 2026-11-13

**Result:** PDL was never active before today. Made to work, it adds about 1%
to decode. The first working version produced a different greedy stream in 6
of 27 runs and was made opt-in; the cause was kernels launched as programmatic
dependents without `griddepcontrol.wait`. With that fixed (last section) 20 of
20 runs give the reference stream and PDL is on by default again;
`ALLPAKA_CUDA_PDL=0` turns it off.

## What was wrong

`gpu/cuda/pdl.rs` needs two things cudarc keeps private: the raw `CUfunction`
and the kernel argument vector of a `LaunchArgs`. It read the vector at byte
offset 64, a guess about how rustc lays the struct out. With the pinned
toolchain the guess is wrong: the first launch found no plausible vector,
printed `PDL launch failed; disabling PDL and falling back to cudarc launch`
and switched PDL off for the process. Every CUDA number published so far was
therefore measured without PDL, although the log said `PDL launches enabled`.

The lookup now finds both fields by comparing the candidate words with what
the types print through their public `Debug` impls, once, on the first launch.
A mismatch disables PDL; nothing is read at an unverified offset.

All 20 printed the same prefill hash (`3848986decfbbfc1`) and 80.6 tok/s.

A PDL run that differs chose another token somewhere in 128 steps. With programmatic
stream serialization a kernel may start before its predecessor has finished
unless it waits itself (`griddepcontrol.wait`), so a kernel that reads its
predecessor's output without waiting is a plausible cause. Not investigated.

## Follow-up the same day: the cause, and PDL back on by default

**Cause.** The launch attribute was put on every kernel that went through
`launch_builder_pdl`, but only some of them execute `griddepcontrol.wait`. In
the decode graph `quantize_q8_1`, `quantize_q8_1_q6`,
`rmsnorm_rope_qk_store_table_dpos` and `argmax_f32` did not, and their
predecessors (the mmvq matvecs, the RMSNorm kernels) release dependents before
their last write. Such a kernel could read its input while it was still being
written.

**Fix.**

- `pdl.rs` no longer reads cudarc's private layouts at all, verified or not:
  kernel modules are loaded with `cuModuleLoadData` (the `CUfunction` comes
  from `cuModuleGetFunction`) and the launch builder collects the argument
  pointers itself.
- The host scans each PTX for `griddepcontrol.wait` per entry point. A kernel
  without it always gets a plain launch, whatever the call site asks for.
- The four decode kernels above got the wait (nvcc `mmvq_q8.ptx` rebuilt), so
  the whole-token decode graph is one programmatic chain.
- `ALLPAKA_CUDA_PDL_DEBUG=1` prints, per captured graph, the programmatic edge
  count (`cuGraphGetEdges_v2`) and per-kernel pdl/plain launch counts.

**Is it active?** Decode whole-token graph: 579 of 579 edges programmatic with
PDL on, 0 of 579 with `ALLPAKA_CUDA_PDL=0`. nsys with `--cuda-graph-trace=node`
(measured on the base before `c32ffc5`): 578 of 583 decode kernels per token
start before their predecessor ends; idle gaps between kernels 22 us/token
against 233 us/token without PDL.

prefill-only `swiglu`, `store_kv_batch_f16`, `residual_add` have no wait and
keep plain launches.
