# Narrow-shape rate deficit, measured at fixed dispatch: which axis owns it?

Question. The published streamed table (correction #10 item 5 of
../2026-09-24-indexed-matvec/README.md) says a dimension at 768 costs 18-23%
of the byte rate: `q4_k` [768,2048] at 386.7 against 472.2 at [4096,1536],
`q6_k` [2048,768] at 363.9 against 471.7. That table cannot answer *why*, and
not because of contention: its narrow rows are 6144 blocks per dispatch and
its reference row 24576, so a 'shape' difference there is also a dispatch-size
difference. The named candidate was the block count - `n_in` 768 is three
256-element K-quant blocks per row against 6-16 elsewhere - and the rival was
row count, since a 768-wide row is also a 2x smaller `n_out` in one of the two.

DoD. Say which axis the deficit tracks, and price it against the 30B's decode
wall, or state that it tracks neither and name what does. Two ladders of
knobs are in scope: dispatch geometry (`ALLPAKA_Q4_NR0`, `ALLPAKA_MV_TG`) and
the period-4 phase model the kernel's own block step implies. Nothing in
between: a number for the deficit without an axis is not an answer.

Harness. `cargo test --release -p allpaka-backend --test gpu_ffnbench --
 narrow_dim_isomer_ladders --ignored --nocapture`, five isomer ladders whose
members all dispatch the same number of quant blocks - so identical bytes per
dispatch, identical footprint, identical `n_out * (n_in/256)` - while `n_out`
varies 4-5x within a ladder and `nb = n_in/256` runs 2-16. Ladder 1
(49152 blocks per dispatch) is the 30B's own size and contains both of its
rows: `q4_k` [768,2048] at nb=8 and `q6_k` [2048,768] at nb=3. 384 MiB
streamed per shape, four interleaved passes, `slots=8`, shared activation.
`ALLPAKA_BENCH_LADDER_ONLY`, `ALLPAKA_BENCH_REPS`, `ALLPAKA_BENCH_FEEDS` and
`ALLPAKA_BENCH_REVERSE` are the arm knobs; each log file in this directory is
one process.

Admission. Nothing here is an absolute. The in-run `q8_0` meter of these
windows sits anywhere from 0.42 to 1.25 of the 495.6 GB/s ceiling (section 1)
and pass 1 to pass 8 of one row decays by up to 2.4x (section 0), so every
crossed statistic is a per-pass paired ratio against the nb=4 member of the
*same* ladder, and section 8 shows the pairing stops at the ladder boundary.

Generated by `analysis.py` in this directory from the logs beside it; the
tables below are its stdout, so no number is retyped from the bench.

### 3. The sawtooth probe: `nb` 3..12 at constant total blocks (55440)

  `matvec_q4_k_mv` walks a row's blocks as `for (ib = ix; ib < nb; ib += 4)`,
  with `ix = tiisg/8` so a row's block loop runs `ceil(nb/4)` whole iterations
  of four slots - four block phases - and `simd_sum` closes the four `ix`
  groups. The 4-phase model therefore charges a row `4*ceil(nb/4)` block slots
  and its cost per block, against `nb=4`, is `(4*ceil(nb/4)/nb) / 1`.
  A deficit at `nb=3` is one idle slot per phase of the one iteration it runs,
  and `nb=6` is two idle slots in each phase's last iteration.

### 7. Geometry probes: is the `nb=3` cost an occupancy or row-sharing artifact?

  In `matvec_q4_k_mv` a row's blocks are walked by `ix = tiisg/8`, so the
  block step is four 8-lane slots per SIMD group whatever the settings, and
  `NR0 = 32/LPR` only chooses how many *rows* share those four slots. So
  `ALLPAKA_Q4_NR0` sweeps rows-per-group (1, 2, 4) and `ALLPAKA_MV_TG` sweeps
  the threadgroup size (64, 128, 256); neither is a phase-count knob, and
  what a flat answer here rules out is activation-reuse and occupancy, the
  two other reasons a 3-block row could cost more than a 4-block one. The
  phase model itself is tested by `nb=6`, which idles the same quarter of the
  group and shows nothing (section 3).

  `q6_k` has no rows-per-group knob (its `lanes_per_row` is a hard 16), so it
  is this probe's negative control: only `ALLPAKA_MV_TG` can move it. Each arm
  is its own process and the incumbent is re-run last as the drift check.

### 8. Where the pairing stops: cross-ladder ratios are not a statistic

  Every claim above compares shapes inside one ladder, where the members are
  visited seconds apart. Comparing *ladders* at the same `nb` reuses the pass
  index across a gap of minutes, so it is unpaired in exactly the way the
  header of this file says not to be. The test is the same pair measured in
  two processes that each held every ladder: if the pairing travelled, the two
  windows agree; they do not, by 8-40%, while the within-ladder pair of the
  same two windows agrees to 0.2%.

  narrow row is 6144 blocks and its reference row 24576 - cannot be measured

  within a few percent of each other, which is the gate
  ../2026-09-25-narrow-shape-axes/results.txt
  already sets and this machine has not yet met. What this file does settle is
  the shape axis at fixed dispatch, sections 2-7.

### 9. Visit-order control: does the `nb=3` shape own its cost, or the slot?

  The ladder arrays are written wide to narrow, so in the forward walk the
  `nb=3` member is always the last shape visited in its pass. Reversing the
  walk (`ALLPAKA_BENCH_REVERSE=1`, which reverses the row list and so also
  the within-shape format order) moves `nb=3` to first. If the deficit is a
  shape cost it survives the swap at the same value; if it is a position cost
  it moves to whichever shape ends up last. Forward and reversed are adjacent
  processes, and the incumbent geometry arm sits between the pair as a third
  reading.

  Price. The 30B's rows are `q4_k` [768,2048] at nb=8 (1.00 x its own
  reference, i.e. no shape cost) and `q6_k` [2048,768] at nb=3 (1.224 x).
  Only the second is a victim, and it is 27.3% of the model's decode
  bytes = 1.44 ms of a 6.70 ms/token wall
  (../2026-09-24-per-token-byte-census/time-ledger.txt section 4). Removing a
  1.22x cost there recovers 1.44*(1-1/1.22) = 0.26 ms/token
  = 3.9% of the wall, at or under this machine's e2e noise.
  The 0.95 ms / +14% ceiling quoted by
  ../2026-09-25-narrow-shape-axes/results.txt assumed both rows were shape
  victims; the paired data above says one is and one is not.

  Mechanism, and the list of what it is not. The kernel walks a row's blocks
  in four 8-lane slots (`ix = tiisg/8` in `matvec_q4_k_mv`), so a period-4
  phase model predicts 4*ceil(nb/4)/nb = 1.333 at nb=3 *and the same 1.333 at
  nb=6*. Measured: 1.27 and 1.05. Section 3 sweeps nb 3..12 at constant total
  blocks and finds no period-4 sawtooth, so quantisation is not the law and
  nb=3 is a hole rather than a tooth. Row count is exonerated by section 2
  (`n_out` varies 4-5x at fixed bytes with nb in {4,6,8} flat to a few
  percent), the byte pipe by `q8_0` at the identical 768-wide shape, occupancy
  and row sharing by section 7's six dispatch-geometry arms, visit position by
  section 9's forward/reverse pair. No knob in this build reaches the hole.

  Verdict, and the one axis this instrument cannot see. The published '768
  costs 18-23%' splits in two: its `q6_k` half is this nb=3 hole and is worth
  ~4% of the 30B's wall, and its `q4_k` half is not a shape cost at all - it is
  ladder 1 against ladder 3, i.e. 49152 blocks per dispatch against 196608,
  which is exactly the comparison section 8 shows pairing cannot support. The
  nb=3 cost ratio does drift with that axis (0.96 -> 1.27 -> 1.30 -> 1.32 across
  the four ladder sizes in section 5), but those are four different windows in
  one process, so it is a lead and not a result.

  Reopen DoD, either arm. (a) A `matvec_q4_k_mv` / `matvec_q6_k_mv` arm that
  changes the fixed four-slot block step for 3-block rows - a different lane
  split, not another value of `ALLPAKA_Q4_NR0` or `ALLPAKA_MV_TG`, both of which
  are measured flat here - and must bring the ladder-1 nb=3 paired cost from
  ~1.22 to below 1.05 with `gpu_parity::indexed_matvec_matches_cpu_reference`
  clean, then be gated e2e on the 30B against this file's ~4% ceiling. (b) Two
  processes whose absolute `q8_0` meters agree within 3%, which is the only
  admissible way to price the blocks-per-dispatch axis; ~16 s per run, and the
  gate is the one ../2026-09-25-narrow-shape-axes/results.txt already sets.
