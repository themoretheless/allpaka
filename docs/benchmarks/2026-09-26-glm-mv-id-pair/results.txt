# ALLPAKA_MV_ID on GLM-4.5-Air: campaign abandoned under the stop rule

Question (preregistered in [preregistration.txt](preregistration.txt) before any
counted pair): does the shipped default `ALLPAKA_MV_ID=1` - llama `mul_mv_id`
geometry, `grid.z = slots`, for the INDEXED Q4/Q8 `_mv` kernels
(`crates/allpaka-backend/src/gpu/metal.rs:9477-9509`) - cost or gain anything e2E on
GLM-4.5-Air decode, and is the +/-3% ship rule met for the first time on this knob?

## Verdict

**No measurement. The campaign was abandoned under its own pre-registered stop
rule**, which reads: if fewer than 3 of the first 4 real pairs are admitted, stop and
publish the abandonment rather than extend the run hunting a quieter window. It
admitted **2 of 4**. The machine went bad two minutes into the campaign - a compiler
that started after the driver's only build check (see below) - and 8 of the 22
measured processes ran depressed. MV_ID's default stands **as shipped and still
unpriced**, exactly as `docs/decode-opts.md` described it before this attempt, which
is the one thing this artifact does not change.

What this artifact is instead: a characterisation of the disturbance that killed the
run, three instrument bugs and one false cause it retracted, and a re-run definition concrete enough that the
next attempt does not repeat this one.

## What ran

- 4 calibration processes (A3's thermometer): prefill 373.59 / 373.82 / 373.98 /
  374.29, median **374.15**, so the band floor is **317.88**; their decode read
  46.14-47.48, i.e. the window opened healthy.
- 1 priming pair (discarded by design): on 46.47 / off 45.93.
- Rounds 1-4 counted - 4 `real` (on/off), 4 `null` (on/MV_ID=1, an identical
  encode), 2 `control` (on/Q5_0_MV=0, the positive control) = 10 pairs, 20 processes.
- Killed during round 5, on the analyzer's stop-rule line and not on a judgement made
  afterwards; the later rounds are not analysed and not counted.
- Arm identity: `metadata.resolved_overrides` matched the preregistered env in all 22
  processes (A0 fired 0 times), all four arms dispatched **26368** kernels per
  token-set (MV_ID changes `grid.z`/threads-per-block, not the dispatch count),
  `outside the GPU` read **0%** in every process, and `fast_path` was 32/32 with
  `declines=0` everywhere (A1 fired 0 times) - so no arm was dead and no arm was the
  wrong arm.

## Three instrument bugs, and one cause this file invented and then checked

1. **The driver's build check ran once.** [drive-mv-id.py](drive-mv-id.py) refused to
   start while `cargo`/`rustc`/`llama-bench` was live and never looked again, so a
   build that starts mid-campaign is invisible to it. Fixed: `wait_quiet()` now
   requires a clear compiler at every launch (calibration, priming, each round), not
   only a load under the gate.
2. **A5's window was a point, not a span.** [analyze-mv-id.py](analyze-mv-id.py)
   attributed covariates to each arm's `st_birthtime..st_mtime` of the *report JSON*,
   and the engine writes that file when the process closes, so the window was 0.0 s
   long and A5 sampled a timestamp instead of an arm. The stdout log, created at
   process start, gives the real ~16 s span, and the analyzer now uses `win_log`.
   Effect on this campaign: the attributed maxima moved (round4 null 11.95 -> 13.94,
   round2 real 0.00 -> 2.07) and **no admission changed** - still 2 of 4 real, still
   abandoned. The stop-rule count is window-independent by construction anyway, since
   A5 is applied to pairs while the rule reads `arm_problems` (A0-A4).
3. **A cause this file first asserted and then disproved with its own timeline.** The
   draft explanation of `criterion 0` failing was structural: A4's 30 tok/s floor comes
   from the *default* arm's history, so an intentionally-slow control arm "gets vetoed
   for being slow" and 0-of-2 was unsatisfiable by construction. The records in this
   file say otherwise. The healthy control process (round3, t+292 s) read prefill 374.2
   = 1.000 of the calibration median and decode **39.74** - ten tok/s clear of that
   floor - so a ~16% knob does not trip A4 at all. Both vetoed control processes sat at
   0.48 and 0.62 of the clean level, which is the same depression that vetoed `on`
   processes elsewhere in the campaign; round3's control pair in fact fell to the *`on`*
   arm's A3 (250.2), not to the control's band. What is actually missing is narrower:
   nothing in the artifact states what a healthy `q5off` reads, so telling "control
   disturbed" from "control working" takes a hand read of the timeline, and control
   pairs run only in odd rounds, so two admissible ones need two more lucky windows. On
   cost: the three control ratios this campaign printed (1.1469 in the uncounted smoke
   pair, 2.0845, 0.8328) each pit a healthy arm against a depressed one, so none of
   them is `ALLPAKA_Q5_0_MV`'s cost.
4. **A4's floor carried the anchor error documented the same morning.** The 30 tok/s
   came from a band anchored on 45.95, which is a **tg64** print, applied to a tg32
   arm ([../2026-09-26-glm-llama-parity/results.txt](../2026-09-26-glm-llama-parity/results.txt),
   "The incumbent moved too"). At 30 it is loose enough to have mattered little; the
   lesson is that a floor's provenance has to name its generation length.

## The reading this artifact refuses

Both admitted real pairs sit below parity: 0.9680 (AB) and 0.9485 (BA), median
**0.9582** = -4.18%, same sign in both orders, and that excess does clear the 2.47%
null floor - so the pre-registered decision rules, run mechanically, print
`FLIP-TO-OFF CANDIDATE`. Every real pair of the whole campaign, admissible or not,
read `off` faster (0.8655, 0.9291, 0.9485, 0.9680, and the smoke pair at 0.9952),
while the identical-encode null pairs straddle 1 in both directions (0.8234, 0.8521,
0.9782, 1.0247). That asymmetry is a *reason to re-run*, and it is written down so the
next attempt starts from a hypothesis rather than a blank sheet.

It is not a verdict, for three independent reasons: the campaign was pre-registered to
stop at 2 of 4; criterion 0 never obtained an admissible control, so the run has not
shown it can see a ~16% knob on this model in this window; and n=2 admitted pairs
cannot move a shared default that also serves qwen3-30b, which the ship rule already
requires re-measuring before `metal.rs` is touched.

## What is not claimed

- Nothing about MV_ID's size, sign or ship-worthiness. The -4.18% above is an
  abandoned campaign's arithmetic, not a measurement.
- Nothing about `ALLPAKA_Q5_0_MV`'s cost: every control ratio here pairs a healthy arm
  with a depressed one.
- No llama arm was run, so nothing here speaks to engine parity. The clean-level
  absolutes (on 45.20 / off 47.17) only say this binary still decodes GLM at the
  ~46 tok/s the parity run measured (46.04) when the machine allows it.
- No generated-text check: the bench writes no continuation field, so arm identity is
  carried by `resolved_overrides` plus identical dispatch counts, as item 2 of the
  04:29Z amendment set out before the run.

## Definition of done (the re-run)

The re-run is registered as its own campaign,
[../2026-09-26-glm-mv-id-rerun/preregistration.txt](../2026-09-26-glm-mv-id-rerun/preregistration.txt),
whose four changes to this design are exactly items 1-3 below plus the launch settle, and
which replays this campaign's data to show the gates move nothing here.

1. A window where `build_busy()` is clear at **every** launch, and where the
   calibration decode absolutes land in the 45-48 band this campaign began with.
2. The control arm's expected absolutes measured *in the campaign's own calibration*
   (one `q5off` process beside the four `on` ones) and printed next to each control
   verdict, plus control pairs in every round rather than only odd ones. Criterion 0 is
   then a check on the machine, not a coin toss on the window.
3. >= 8 admissible `real` pairs, >= 4 admissible `null`, >= 2 admissible `control`. If
   the third is not reached, the outcome is published as "not resolvable", never as
   "no effect".
4. The +/-3% decision with AB/BA sign agreement against the null floor, on GLM; and
   if it lands beyond 3% either way, the same test on qwen3-30b before any default
   changes, because `MV_ID` is a shared knob.
5. A3 kept as a *removal* gate only, with its allpaka-side direction reported beside
   the headline, as the parity artifact does.
