# Qwen3-30B-A3B Q4_K_M: Allpaka copy / zero-copy / llama.cpp

Новые замеры на Apple M4 Max. Три режима используют один официальный GGUF и его проверенный SHA-256. Исходная модель прежней таблицы отсутствует локально; новый файл имеет другой хеш. Эти цифры нельзя склеивать с историческими 1437,2 / 1533,7 токенов/с или приписывать изменение между версиями только zero-copy.

## Протокол

- Allpaka «до»: `ALLPAKA_PREFILL_ZERO_COPY=0`, копирующая materialization residual.
- Allpaka «после»: `ALLPAKA_PREFILL_ZERO_COPY=1`, shared residual и прямое чтение output-head входа.
- Один зафиксированный release-бинарник `shared_activation_bench` для обоих режимов; SHA записан в metadata, неизменность проверяется после серии.
- llama.cpp: установленный `llama-bench`, 0.7.0, build 11669, commit `620d2225c`; версия, бинарный SHA и команды сохраняются.
- Итоговая серия: PP=480/TG=32; chunk/microbatch=512; llama batch=512; TG=32 из однотокенного контекста; f16 K/V; Metal, все слои на GPU; llama flash attention включён. CPU threads=16.
- Шесть принятых блоков PP480/TG32, все шесть перестановок порядка трёх режимов. В каждом процессе Allpaka один прогревочный и три измеряемых прохода. llama выполняет три измерения каждой фазы со своим стандартным прогревом.
- Allpaka prefill использует фиксированный поток `((i+32)*733+17) % min(vocab,30000)`. Decode — штатный `forward_greedy_n`, стартовый контекст `[1]`, 32 GPU-шагa. CPU fallback делает замер невалидным, проверяются attempts/successes/declines каждого прохода.
- Между режимами Allpaka проверяются все конечные prefill-logits (допуск 1e-4), совпадение decode-токенов во всей серии и реальные shared-handoff/head counters.

`comparison_validated=false` относится к сравнению с llama: `llama-bench` использует собственный поток токенов, поэтому эксперты MoE и точная работа различаются. Это наблюдаемая пропускная способность при одинаковых границах контекста и настройках памяти, а не доказательство превосходства на идентичном вычислении. Фоновая нагрузка рабочего компьютера не изолирована.

## Воспроизведение

```sh
cargo build --release -p allpaka-model --example shared_activation_bench
python3 scripts/bench-zero-copy-vs-llama.py \
  target/release/examples/shared_activation_bench /opt/homebrew/bin/llama-bench \
  /path/to/Qwen3-30B-A3B-Q4_K_M.gguf /tmp/qwen30-three-arm-new \
  --pp 480 --blocks 6 --rounds 3 --threads 16
```

Не запускать параллельные GPU-бенчи. Источник и хеш модели — в `model-source.json`; принятые выборки и команды — в `selected/`.

## Как исключалась конкурирующая GPU-нагрузка

Первоначальный непрерывный запуск испытал резкий провал скорости у обоих движков. При проверке GPU-клиентов обнаружен активный `street_walk` из Voxy. Питание было от сети, предупреждений о перегреве не было. Первую прерванную серию сохраняет `interfered/`; повторную непрерывную попытку с перезапуском рендера — `repeated-series/` и `renderer-overlap-repeated-series.json`.

Для итогов приняты два полных блока повторной серии, завершившиеся до независимо установленного старта PID 8914 в 06:00:23 местного времени. Оставшиеся четыре порядка собраны после завершения рендера, с проверкой появления `street_walk` каждые 0,5 секунды. При пересечении отменялся бы весь блок, независимо от его численных результатов. Привязка исходных файлов и критерии — `selected/manifest.json`, координатор сохранён как `idle-coordinator.py`.

Рендер не приостанавливался. Для своей серии использовалась конечная по времени assertion `caffeinate`; после работы она освобождена. PP2048 из прерванных попыток не включён в сравнение: его нельзя считать валидной дополнительной серией.

Это устраняет известное пересечение со `street_walk`, но не изолирует весь рабочий стол. Даже в принятых блоках сохраняется большой дрейф абсолютной скорости; таблица не является оценкой гарантированной пиковой производительности M4 Max.

Медиана медиан процессов, токенов/с; в скобках min–max медиан принятых блоков. На движок и фазу — 6 блоков × 3 измерения = 18 выборок.

### Парные отношения внутри блоков

Медиана отношения скоростей внутри блока; bootstrap 95% по шести блокам, 10 000 повторных выборок с фиксированным seed. Эта статистика отличается от отношения двух общих медиан.

| Фаза | После / до | 95% | После / llama | 95% |
|---|---:|---:|---:|---:|
| prefill | +0.32% | -0.76…+7.13% | -9.03% | -15.33…-3.01% |
| decode | -0.72% | -2.25…+2.22% | +9.82% | +1.71…+30.20% |

**Убедительный прирост всей модели от zero-copy не обнаружен:** интервалы отношения «после / до» включают ноль. По общим медианам после zero-copy prefill на 9,1% медленнее llama, decode на 15,5% быстрее. Это наблюдение данной серии с разными потоками токенов у движков; `comparison_validated=false` остаётся в metadata.

## Проверка выполнения

- Все 12 принятых процессов Allpaka вернули одинаковые конечные prefill-logits: максимальная разница 0, SHA-256 массива совпадает. Последовательности decode-токенов одинаковые.
- 1536/1536 GPU decode-шагов с учётом прогрева; 0 declines. Из них 1152 шага относятся к измеряемым раундам.
- Shared-путь реально использовался: 24 handoff; устранено 94 568 448 байт handoff + повторного staging head-входа с учётом прогрева. На один PP480 это 3,75 МиБ residual и 8 КиБ head-входа. В copy-процессах соответствующие счётчики равны нулю.
- У llama проверены Metal, 99 GPU layers, `n_cpu_moe=0`, f16 K/V и включённый KV offload; границы PP/TG/depth и количество выборок совпадают с протоколом.
- Все принятые процессы завершились успешно; SHA бинарников проверены на неизменность. Нормализованные JSON, исходные команды, логи и сжатые полные stdout принятых Allpaka-процессов сохранены в `selected/`.
